# ノートの自動保存時の上下移動修正（2026-11-01）

## 症状と原因

利用者が2.0.0の確認用VSIXの表示を確認した際、VS Codeを2カラムに分割してノートを表示すると、自動保存のたびに画面が上下に動くと報告。分割を解除してノートを広く表示すると症状は出ないと確認した。「ボード全画面」や「編集を隠す」の違いではない。

保存完了時の処理はノート全体を再描画していなかった。原因は、上部ヘッダーの「未保存」バッジとタイトル横の*がhiddenで出入りし、ヘッダーに使える幅が変わること。狭い幅では操作ボタンが折り返され、ヘッダーの高さと本文領域の開始位置が変わっていた。

実際の生成HTMLを使ったChromeの合成ノートで再現。幅760pxではヘッダーが107pxと147px、本文の開始位置が125pxと165pxへ変化（40px）。幅900pxでは63pxと107px、本文開始位置81pxと125pxへ変化（44px）。1450pxでは変動なしで、利用者の報告と一致した。

## 修正

`src/views/note-webview/note-webview.css` に、通常編集ヘッダーの `#dirtyBadge[hidden]` と `#dirtyMark[hidden]` に限った表示規則を追加した。保存済みでは文字を見せず、その表示分の場所を確保することで折り返しを固定する。

保存・自動保存・dirty判定・保存中の追加入力・競合検出・スクロール位置復元のコードは変更していない。未保存時の表示は維持。ボード側の別バッジには適用しない。保存済みでもヘッダーには表示幅の予約が残るため、狭い画面のヘッダーは未保存時と同じ高さになる。

## 検証

- 幅480／560／620／700／760／900／1000／1450pxで、自動保存相当の入力・保存完了を3回ずつ実行。全幅で未保存・保存済みの両状態を計測。
- 修正後は8種類すべてでヘッダーの高さと本文開始位置の変動0px。760pxの個別再確認では、スクロール位置400pxも保持したまま未保存／保存済みを往復し、ヘッダー147px・本文開始165pxで固定された。
- 実際の生成ノートHTMLと画面スクリプトを使用。VS Codeホストへの保存要求と完了通知は合成データで模擬している。実作品や認証設定は使用していない。
- ノート・webview・保存・同期・競合関連259テスト成功、失敗0・スキップ0。初回のサンドボックス実行は一時ファイルrenameの権限制限で失敗し、コードを変えず作業フォルダ内TEMPと通常権限で再実行して成功。
- CSSだけの局所変更のため、新しい文字列一致テストや全体テストの再実行は行わず、実ブラウザでの位置計測と関連テストを検証に使った。直前の全体テスト実績は1,987件成功。
- 差分・修正前後の計測・画面・ログは `.review-baseline/note-autosave-layout-20261101/`。
