# OneDrive書込直前の重複した版確認の削減（2026-10-27）

## 調査

利用者がOneDriveはDropbox・Google Driveに比べ少し遅いとの所感を示し、書込側の調査・短縮へ進むことを承認。クラウド間の速度比較は今回は実測していない。

構想→項目は、構想本文保存→項目書込→構想の同期情報保存という順序。反映先の書込が成功する前に同期済みを確定させたり、古い指紋を残したまま同期情報保存を省略したりすると、途中失敗や両側変更の判定に影響する。今回はファイル書込回数と順序は維持する。

前回の版確認による本文再利用では、同期直前にgetItemMetadataで最新eTagを確認していた。しかしwriteTextが直後に同じファイルのgetItemMetadataをもう一度行い、続いてPUTしていた。この重複した確認を短縮する。

## 変更

OneDriveProviderはgetItemMetadataの応答を内部で複製して一時的に保持する。保持キーは接続インスタンス内のdrive・itemを含むリソースパス。次のイベントループで破棄する0msタイマーと、単調時計による最大50msの期限を併用する。タイマーが背景タブなどで遅れても、長時間の再利用をしない。

writeTextは、同じリソースについて直前に確認した情報が有効なときだけそれを使い、期待するeTagと比較する。一度使った情報は消費する。確認がない・時間が空いた・別リソースの場合は従来どおり新しくGETする。返却したメタデータを呼出元が変更しても、内部の複製は変わらない。書込完了・失敗でも一時情報を破棄する。

GETでの確認と期待eTagの比較を省略する仕組みではなく、同じ処理の流れで完了した確認を二度行わない仕組み。PUTには従来どおりIf-Matchを付け、409／412は競合として停止し無条件再送しない。確認後の競合についても模擬応答で412停止を検証した。OneDriveの条件不一致エラーについては[Microsoftのエラー仕様](https://learn.microsoft.com/en-us/onedrive/developer/rest-api/concepts/errors?view=odsp-graph-online)を参照した。本文更新の競合保護を緩める新しいAPIには切り替えていない。

計測に「OneDrive・既存ファイル書込」を追加。metadataReusedは直前の確認を再利用したか、preflightMsは書込内の版確認時間、putMsはPUTと応答処理の時間、failedは失敗したかを示す。通常のgetItemMetadataで行った確認時間は、前段の出典取得・構想版確認に含まれる。従来の画面別の書込段階と新しい書込計測は内包関係なので合算しない。本文・ファイル名・ID・URL・トークン・eTagは計測へ記録しない。
