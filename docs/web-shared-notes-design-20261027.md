## 推奨する利用体験

最初は原稿の歯車から開く「ノート参照」に「参照元作品」を追加する。現在の作品を初期選択とし、作品設定で関連付け済みの作品を選べるようにする。プロット／資料の切替とノート選択は既存の操作を使う。作品Bの原稿を編集中に作品Aのノートを読んでも、原稿と保存先は作品Bに残る。参照元の作品名を表示し、どの作品のノートか分かるようにする。

初回は現在接続中のクラウド・同じ作品ルートにある作品が対象。他アカウント、他クラウド、別ルートの横断参照は含めない。ノートの原本は所有作品に置き、参照先への複製・同時保存・メモ自動反映は追加しない。表示内容も既存ノート参照の範囲を基本とし、画像添付や関連リンクの機能拡張は別に扱う。

## IDと関連の扱い

- 関連先の照合には、保存済み設定ファイルに実際に存在するworkIdを使う。フォルダID、フォルダ名、作品名で置き換えない。欠損IDを参照するだけで新規作成・保存しない。
- 正常な相互関連は従来どおり扱う。初回の候補は現在作品の保存済みrelatedWorkIdsに直接登録された作品とする。A→B→Cを理由にAからCまで自動で広げない。
- 片側だけの関連は検出・区別する。相手だけに登録されている作品を自動で追加したり、閲覧しただけで相手設定を直したりしない。相互更新の仕様はW16-Bで扱う。
- 同じworkIdを持つ作品が複数ある場合は曖昧として参照しない。コピーされた作品設定が原因でも、任意の1作品を選ばない。
- 関連IDの相手が未許可・欠損・削除などで見つからなくても、参照処理で元の設定からIDを削除しない。読み取り失敗を「ノートなし」と区別する。

## 最初の実装単位：W16-A 既存関連作品の読み取り参照

1. 保存済み作品設定のID・関連IDを読み取り専用で解決するモジュールを追加。既存カタログで設定を取得できる場合はその結果を活用し、接続直後に全ノート本文を先読みしない。
2. 対象のprovider・作品を明示して渡すノート参照読込を分離。selectedWorkや編集中ノートを一時的に他作品へ置き換えない。参照時はフォルダ・設定・ノートを作成しない。
3. 原稿のノート参照に参照元作品セレクトを追加し、現在作品と直接の関連先のプロット／資料を表示。まずVS Code等で保存済みの関連設定を利用する。
4. 利用者・接続先・ルート・参照元作品・ノート種別・ファイルを区別してメモリ内キャッシュを管理。作品や接続、参照元の切替、パネルを閉じた後の遅い応答は画面へ反映しない。
5. 未許可・削除・取得失敗の参照先だけに案内を出し、自作品の原稿編集や参照へ戻れるようにする。Google Driveの個別追加許可を越える探索・自動作成は行わない。

想定する変更先はweb/app.mjsのノート参照、web/index.htmlの参照元作品選択、必要最小限のweb/styles.css、読み取り用のweb/libモジュール、work-discovery／設定取得との接続、Service Workerと対応テスト。作品設定の保存や既存同期形式はこの単位で変更しない。

完了条件は、Bの原稿とカーソル・未保存入力・保存先を保ちながらAのノートを読めること、プロット／資料の切替ができること、同名作品・重複ID・取得失敗で別の本文を表示しないこと、参照中の通信に作成・更新・削除がないこと。実ブラウザでは仮データで未保存原稿、切替中の遅延、狭幅を確認する。

## 次の単位：W16-B Webの作品設定から関連作品を登録

Webの作品設定に関連作品の選択・解除を追加し、VS Codeと同じworkId／relatedWorkIdsで相互更新する。関係は両側の設定ファイルに保存するため、クラウドでは原子的に一括保存できる前提を置かない。

各設定を最新の版で読み、未知項目と既存の未解決関連を保って条件付き更新する。片側だけ成功した場合は未完了を明示し、現在の接続・作品と最新の版を確認して再試行できる設計にする。失敗を隠して完了扱いにしたり、他端末の変更を無条件で戻したりしない。作品設定自動保存と複数作品の関係更新をどの単位で確定するかは、W16-B着手時の具体設計で確認する。

その後、必要に応じてノート一覧・ノートプレビュー等にも関連作品の読み取り参照を広げる。初回からすべての画面へ横断導線を加えることはしない。
