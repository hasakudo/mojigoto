# Web読込用Markdownを自動更新する案（2026-10-15）

実装追補（2026-10-16）：3aの読込・プレビューと3bの生成物読込・ドロップは利用者実機で確認済み。[自動生成の実装](code-review-web-markdown-generation-20261016.md) に続き、[3cの対応先管理](code-review-note-template-sync-20261016.md) を実装した。3cの利用者実機確認とG:でのDrive項目維持は未確認。以下は設計時点の記録。

追補：利用者の想定はWebの通常の新規作成からファイル内容を読む流れ。新規作成画面／作成直後の空の編集画面への読込導線を優先する。将来の項目メモ・関連リンク・ふりがなの読込は生成側も版付き形式へ拡張する。[更新した操作・将来拡張の設計](code-review-stage4-implementation-plan-20261015.md)を参照。以下の最初の本文形式に限る記述は初期版の範囲であり、将来の対応を禁止するものではない。

追加要望の検討記録。利用者は保存単位を「ノートごとに最新版を1ファイル」と指定した。今回は設計のみで、自動生成・ON/OFF・Web読込は未実装。既存の手動Markdown書き出しも変更していない。

## 結論と位置付け

**VS Codeで保存したノートからMarkdownを自動生成し、同じファイルを最新内容へ更新する設計は可能。** 毎回の手動書き出しを省ける。ただし通常の世代別バックアップとは用途が違うため、UIでは「Web読込用Markdownを自動更新」と呼び、最新版しか残らないことを説明する。通常の復元用バックアップは既存の仕組みを維持する。

自動書き出し、Webでの新規読込、既存ノートの更新、双方向同期は別の工程。Markdownを増やさないだけでは、Webで新規ノートを増やす問題や、元JSONの未許可を解決できない。まず「自動生成＋Webで明示的に読込」を実装候補にし、常時の双方向自動同期は含めない。

## VS Code側の操作

- Dashboardの保存設定に「Web読込用Markdownを自動更新」を追加する案。初期値はOFF。既存のノート自動保存・構想メモ自動反映とは別設定にする。
- 作品単位でON/OFFを扱う案を優先する。Multiで全作品を勝手に対象にせず、既存作品設定のどの項目へ保存するかは実装前に調べる。
- ONにした際、現在の作品のプロット・資料を一度生成する。以後は内容を正常に保存したノートだけを更新する。入力中の下書きや保存失敗時の内容は書き出さない。
- ノート画面の保存だけでなく、インポート・項目メモ反映など、保存が成功する経路も対象にする。既存の保存入口を点検し、保存成功の共通イベントへ接続する案。外部エディターやWebからの更新を拾う監視は、保存の安定確認・重複排除・G:の挙動を別途確認する。
- OFFでは更新を停止し、既存のMarkdownは削除しない。ONへ戻したら差分を確認して追いつく。
- 生成失敗は「ノート本体は保存済み／Web読込用ファイルの更新は失敗」と区別し、閉じるまで残る警告を表示。自動保存のたびに同じ警告を連打せず、再試行できるようにする。

## 配置と識別

配置候補は作品の`.mojigoto/web-import/plots/<固定ID>.md`と`.mojigoto/web-import/references/<固定ID>.md`。Single／Multiとも作品の既存データ領域を基準にし、_WORKを基準にしない。ExportRootは外部の場合や取り込み除外の場合があるため、初期の保存先には使わない。

- 同じノートは同じパスへ上書きする。日付入りの別名・連番・世代ファイルは作らない。書き込み中の一時ファイルは処理後に残さない。
- タイトルやフォルダ名だけで識別しない。タイトルを変えても、同じ固定IDのMarkdownを更新する。
- IDがない旧データや、作品コピーでIDが重複する場合を考慮する。作品識別子＋ノート識別子の組で対応を管理し、正本のIDや既存リンクを無断で振り直さない。既存IDが移動・コピーを跨いで一意かは実装前に点検する。
- ノートを削除した際は自動生成した対応ファイルだけを対象にする。初期案はMarkdownを残し、Webでは消えた元ノートへ自動反映しない。再生成一覧に状態を表示し、生成物の整理操作は後続にする。未知の手書きMarkdownを削除しない。
- 保存先に同名の手書きファイルや変更済みの生成物がある場合は上書きせず案内する。最新版の生成に必要な版情報・内容の指紋を持ち、ファイルごとに更新順を直列化する。

## Markdownの内容

既存の`# 大分類／## 区分／### 項目／本文`を本文形式の基準にする。タイトルはファイル名に依存させずメタデータで持つ。先頭のHTMLコメントに専用フォーマットの版、作品・ノートの識別子、ノート種類、タイトル、元保存版の指紋、生成時刻を入れる案。パスや資格情報は埋め込まない。

専用コメントは検証してから除去し、既存の本文解析に渡す。一般のMarkdownと専用の生成物を区別する。コメントがないファイルや版が不明なファイルを既存ノートの更新先と推測しない。元のノートIDをWebの新規JSONへそのまま複製して二重の正本を作らない。

最初は分類・区分・補足・項目・本文の対応に限る。画像・項目メモ・関連リンク・呼び名一覧・独立したふりがなの完全なバックアップではない。これらが必要な往復は原本JSONの共有を優先する。コードフェンス内の見出し問題を解消してから共通解析へ接続する。

## Web側の読込と再読込

ローカルファイルから読む既存計画を入口にできる。Drive上の生成物を選ぶ入口は、PC／スマートフォンでの手間を減らせるか別途試す。どちらも「ファイルを選択→内容確認→作成／反映」の1画面にまとめる。ローカルのファイル選択だけではDriveアクセス許可が増えるわけではない。

| 状態 | 推奨する動作 |
|---|---|
| 通常のMarkdown | 新しいノートとして作成する |
| 専用生成物を初めて読む | 元作品とノートの識別子を表示し、現在の作品に既存の対応先があるか確認する |
| 元ノートのJSONを許可済み | そのノートを開く経路を優先。原本を直接共有できるならMarkdown経由の複製は不要 |
| 元ノートが未許可 | 既存ノート更新には原本の追加許可を案内。別ノートとして作る場合は「コピーを作成」と明示する |
| 以前Webでコピーを作成した生成物 | 保存した対応情報からコピー先を提示し、新しいコピーを毎回増やさない |
| 同じ元保存版を再読込 | 変更なしとして終了。作成・上書きをしない |
| 読込元だけ変更・対象は前回読込後に変更なし | 対象を示して明示的に反映する。通常の版照合付き保存を使う |
| 対象も編集済み・未保存・保存／同期中 | 黙って置換せず停止し、内容比較または別コピーを案内する |
| 別作品の生成物 | 対応先の推測更新をしない。新規コピーとして明示するか、正しい作品への切替を案内する |

重要：Webでコピーを作ったJSONは、VS Codeにも別ノートとして見える。これを元ノートと自動で同一視して削除・上書きしない。元の項目メモ等を失わずに同じノートを編集したい場合は、原本JSONを許可して使う現行経路が確実。対応情報をブラウザだけへ保存すると他端末で失われるため、作品ファイルの形式を変えるか、Web作成JSONの任意項目へ持つかは実装時にスキーマ互換性を調べて決める。

Webでの変更を生成Markdownへ書き戻し、VS Codeが原本JSONへ自動反映する方式は、追加の競合管理・項目ID対応・往復による項目欠落の防止が必要。今回の自動書き出し案へ暗黙に含めない。

## Google Driveの確認事項

Google公式ではdrive.fileはアプリで作ったファイルや、利用者がアプリと共有したファイルを扱う範囲。PCで作るMarkdownにも初回の追加許可が必要になる。根拠：[スコープの説明](https://developers.google.com/workspace/drive/api/guides/api-specific-auth)。

既存のDriveファイルの内容更新はfileIdを指定するAPIで行う。根拠：[ファイルのアップロード・更新](https://developers.google.com/workspace/drive/api/guides/manage-uploads)。PCの同名ファイル更新がGoogle Drive for desktop経由で同じfileIdを維持するかは、このAPI仕様だけから保証できない。特に仮ファイルからの置換は、同名でも別項目として同期される可能性を実機で切り分ける必要がある。

したがって「最新版1ファイルを上書きする」だけで追加許可が完全に不要になるとは案内しない。固定パスの通常更新・安全な置換・初回作成・改名・削除再作成をG:で比較し、許可済みファイルが継続して読めるかを確認してから保存方式を決める。権限維持のために保存の安全性を落とす設計にはしない。許可済み原本JSONの読み書きは既存経路を維持する。

## 実装前の確認単位

1. ノート保存の共通入口、ID、作品ごとの設定配置を点検する。
2. 専用Markdownの生成・再生成・OFF・元ノート削除を確認用作品で試す。
3. G:で同一ファイルの許可が維持されるか確認する。これは実Driveで未検証。
4. Web初回／再読込・重複防止・保存後の別編集・元JSONの未許可を試す。
5. 往復が必要な場合に、原本共有で足りるか、専用同期機構まで必要かを判断する。

この調査をW07の実装前に行う。今回の小さな表示改善と一緒に保存・自動同期の仕様を変更しない。
