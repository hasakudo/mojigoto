# バックアップ段階別計測・短縮箇所の調査（2026-10-26）

## 利用者確認と目的

利用者から構想メモ・項目メモの保存完了時間が少し改善したとの報告と再計測を受領。構想は本文1378ms・項目反映5250ms・バックアップ5355ms、項目は本文1750ms・構想反映3536ms・バックアップ5469msだった。並行化後は反映とバックアップを足さず、長い方が主な待ちになる。約5.4秒のバックアップ内訳を特定するため今回の計測を追加する。バックアップ数を設定で減らす案も検討するよう依頼を受領。

## 調査結果

Webの保持方針は対象ファイルごと最大50件・自動履歴90日、保護済みは件数制限と期限整理から除外。通常の作成では管理フォルダ一覧→保存フォルダ一覧→索引読込→新しい本文保存→索引更新。既存の履歴本文は通常取得しない。索引がない・破損している場合のみ、従来どおり履歴本文から索引再構築を行う。Google Driveの追加許可が必要な構成では一部だけで再構築しない。

保持数を減らせば索引サイズと履歴総数は小さくできるが、通常の保存で必要なprovider呼出回数が直接減るわけではない。最初の整理では削除対象が増えて時間がかかる場合もある。実データの件数・索引サイズ・整理時間は今回未取得。現時点では保持数が約5.4秒の主因とは断定できないため、保持数の設定追加と履歴の削減は行わない。VS CodeにはbackupMaxPerFile設定が既にあるが、Webは固定50件。今後Webにも追加する場合は共通索引に対する複数クライアントの整理方針と、保護履歴の扱いを明確にする。

## 実装

既存の「速度計測結果をコピー」に以下の段階を追加。原稿・ノート・構想メモが共有するWebバックアップ処理を対象とする。

- 管理フォルダ一覧・保存フォルダ一覧
- 保存フォルダ・履歴フォルダの初回作成（必要な場合）
- 索引読込（メタデータにある場合はbytesも記録）
- 索引再構築（必要な場合）
- 内容ハッシュ・本文保存
- 索引保存（entries・characters）
- 整理対象一覧・古い履歴削除（removed）
- 処理全体（targetType・reason・result・indexEntries・removedEntries）

resultはcreated=作成、interval=自動保存間隔内で省略、duplicate=同じ内容で省略、disabled=自動無効、failed=失敗。省略でも索引確認に時間がかかっている場合を区別できる。段階の失敗はfailed=true、処理全体の失敗はresult=failedで記録。整理だけの失敗は従来どおり警告して作成結果はcreatedとするため、古い履歴削除のfailedも見る。removedEntriesは整理対象件数であり、削除成功件数ではない。

計測には本文・ファイル名・保存パス・ハッシュ値を含めない。フォルダ一覧やOneDriveのwriteText/readTextには内部の複数HTTP通信が含まれる場合があり、段階時間はprovider呼出全体の時間である。内包する索引再構築・処理全体・画面側のバックアップ時間を二重に合算しない。

小さな短縮として内容ハッシュ計算を索引の間隔判定後へ移動した。間隔内ではハッシュを計算せず、自動無効で直接呼ばれた場合もフォルダ取得前に終了する。必要な履歴の作成間隔や件数、本文とeTagによる索引競合保護、削除の順序は変更しない。この変更で秒単位に短縮したとは計測していない。
