# W20-B 原稿全体プレビュー：本文の段階読込と横書き表示（2026-10-30）

Web1.0.267／シェルv312／共有CSS1.0.204。3クラウドの目次取得確認を受け、本文表示を実装した。本番・テスト環境への反映、実クラウド・実機Androidでの新機能確認は行っていない。

## 動作

原稿一覧と編集画面の「プレビュー」内の入口を「全体プレビュー」に変更。目次の「読む」で任意の原稿へ移動でき、「先頭から読む」でも開始できる。本文は横書きで、ファイル名・相対パスで区切る。「続きを読む」で次の区間を追加し、「前を読む」で保持範囲より前へ戻る。画面には直近3区間まで保持し、上限を超えた区間はDOMから外す。全原稿を一度に読み込む自動スクロール式ではない。

目次へ戻って別の原稿を選べる。本文が空の原稿と取得エラーを区別し、取得失敗は本文位置にエラーを表示して再試行・次の原稿への移動を可能にした。目次の取得自体が一部失敗している場合、既知の原稿だけの表示であることを本文画面でも明示する。

編集中の原稿は、全体プレビューを開いた瞬間の入力を固定して使う。未保存なら表示内に明記する。一覧から開いた場合は残存するcurrentFileを採用しない。同一セッションの目次に含まれ、ドライブとIDが一致する原稿だけに入力を使う。その他の原稿はprovider.readTextで取得し、openFileは呼ばない。本文・dirty・originalContent・カーソル・履歴・自動保存の設定を変更せず、閲覧のための保存はしない。

書体と文字サイズは既存の原稿プレビュー設定を表示開始時に使う。個別プレビューは維持。縦書き・新しい設定UI・表示位置の復元はW20-C。

## 読込と負荷の制御

- whole-manuscript-body.mjs：要求されたファイルだけを読む。本文は行境界で最大60行または概ね12,000文字ずつ解析し、既存パーサーの見出し・空行・明示ルビ・傍点を保持。記法を別ファイルへ結合しない。先読みは今回行わず、実機結果を受けて判断する。
- whole-manuscript-reader.mjs：取得状態・再試行・中止・前後移動・最大3区間のDOMを編集状態と独立して管理。文字列はtextContent／createTextNodeで作り、HTMLとして挿入しない。
- 本文キャッシュは閲覧セッション内だけ。最大3ファイルかつ合計2,000,000文字を上限として古い本文を破棄し、戻ったときは必要なら再取得する。閉じる・目次へ戻ると破棄する。
- 1ファイル1,000,000文字、1行24,000文字を超える場合は切り捨てず、個別プレビューでの確認を案内。文字数の判定はJavaScriptのUTF-16 lengthであり、メモリのバイト数ではない。1行が長い場合は区切りを壊さず最大24,000文字の1ブロックとなる。
- 描画は最大180本文ブロックにファイル名などを加えた範囲。総ファイル数でDOMが増え続けない。ファイル本文はproviderから全体を受け取ってから分割するため、通信応答の一時メモリまでこの上限で制限できるものではない。
- 同じproviderの本文取得は、中止して開き直した場合も同時2件以内。中止でHTTP自体をabortはせず、後続取得と応答の採用を止める。目次へ戻る・閉じる・作品／利用者／接続先の変更で古い表示を破棄する。
- 読んだ内容は各ファイルの取得時点の組合せ。キャッシュから外れた原稿は戻ると新しい内容になる場合があり、作品全体の同時点スナップショットではない。

## 計測・検証

速度計測に「全体本文・取得」（原稿番号、input／cloud、文字数、区間数、結果）と「全体本文・描画」（原稿番号、区間番号、ブロック数、保持区間数）を追加した。取得には本文取得と行の分割が含まれ、描画はDOM構築処理であり、描画完了やメモリ量そのものを測るものではない。

新規10件を含め全1,812テスト成功。必要時取得・入力の採用条件・目次を開いた時点の固定・一覧からのクラウド取得・行とファイル境界・キャッシュ破棄・上限・空と失敗・再試行・中止・共有通信上限・DOM保持範囲・未保存状態保持を確認。ガイドは共通ソースへ簡潔な操作説明を追加し、生成内容の--checkも一致。

仮データのブラウザでは次を確認した。

- 59原稿の目次からジャンプ、250行の原稿を5区間に分けて表示。4回追加しても本文DOMは3区間まで。長い同一原稿の5区間取得に本文の通信は1回だけ。
- 見出し・明示ルビ・傍点・空行を表示。scriptタグ相当の文字列も文字として表示。
- 次のファイルへ進み、前へ戻り、目次から別の原稿へ移動。
- 本文取得失敗を表示し、再試行で成功。遅い本文の中止は応答待ちをせず、中止して閉じてから応答を返してもダイアログは戻らなかった。
- 406×827のiframeで本文領域461px、スクロールバーを除く幅331px、scrollWidthも331px。未保存の短い原稿では幅346px。横はみ出しなし。
- 未保存の原稿は表示前後で文字列と選択位置26が一致。dirty=true、writes=[]を保持。本文の追加取得なしで入力内容を表示。実クラウドへの通信・保存はしていない。

証跡：.review-baseline/whole-manuscript-body-20261030（full-tests.log、browser-evidence.json、body-mobile.png、変更前後ソース）。iframeの寸法検証はAndroid実機の性能測定ではない。

## 実機での確認事項

1. 目次の「読む」と「先頭から読む」から開始し、本文の順序、ファイルの区切り、ルビ・傍点・空行を確認。
2. 長い原稿で「続きを読む」を複数回押し、スクロール、前への復帰、次の原稿への移動を確認。重くなる操作・原稿のおおよその行数／文字数も記録。
3. 原稿を未保存にして全体プレビューを開き、その原稿に入力内容が表示されることと、閉じた後の本文・カーソル・未保存状態を確認。読み込み中の中止・閉じる・目次への復帰も確認。
4. 3クラウドで表示を確認し、速度計測の「全体本文・取得」「全体本文・描画」を共有。結果に応じて区間サイズ・キャッシュ・先読みを調整してから縦書きへ進む。

接続設定の通知がモーダルに隠れる件は、利用者の後回し指定を維持し未修正。

## W20-B：3クラウド・Androidの利用者確認（2026-10-30）

利用者より「操作は問題ない」と報告。Android 406×827、44原稿・7フォルダの全体目次をGoogle Drive 1,984ms／Dropbox 2,366ms／OneDrive 3,660msで取得完了。最初の本文は3,117文字で、Google Driveは入力欄から1ms、Dropboxはクラウドから1,224ms、OneDriveはクラウドから2,017ms。Google Driveの1msはクラウド取得の比較には使わない。

本文描画は報告全体で28〜168ms。OneDriveで複数原稿の前進と保持区間数3以内を確認。継続区間は本文の再取得なしで描画されている。操作の問題は報告されていないが、168msの描画は一時的な引っ掛かりを生む可能性があるため、描画負荷の課題を解消済みとはしない。現時点では保持3区間・60行の設定を維持し、縦書き導入後も実測する。報告された範囲でW20-B確認済み。反映先の本番／テストの別は今回未指定。

後続スタイル修正：利用者の「あとで」指定に従い、全体プレビューの作品タイトル・ファイル情報・補足表示などを必要最小限へまとめ、本文の可視範囲を広げる。閉じる・目次・前後移動・読込状態・未保存内容の識別はコンパクトに保つ。本文由来の見出しは別扱いとし、装飾用タイトルの省略と混同しない。今回UI変更なし。接続設定の通知重なりも後続のまま。
