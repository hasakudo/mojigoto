# 第1段階・原稿：Webの保存・外部確認・未保存内容

確認日：2026-10-12。第1段階の最初の作業単位として、Web原稿の非同期処理を点検した。第1段階全体の完了記録ではない。

## 結果と修正

原稿保存自体は、送信時の本文を取り出し、保存中の追加入力を未保存として残す実装だった。通信エラー・競合の場合にも元の下書きと保存済み基準を残すことを実行テストで確認した。

一方、保存・外部確認・移動の処理が重なると、下書きや保存後の状態を失う可能性があった。以下を修正した。

| 場面 | 修正前 | 修正後 |
|---|---|---|
| 外部確認中に保存が完了 | 同じファイルIDなら保存前の確認結果を適用できた | 確認開始時の対象オブジェクト・クラウドが変わっていたら破棄。metadata取得後と本文取得後の両方で判定 |
| 保存中に画面移動 | 未保存の破棄を承認すると移動できた | 保存中は移動を止める。接続解除、OneDrive接続、ログアウトにも同じ確認を適用 |
| 原稿の読み込み失敗 | 編集欄を読み込み表示に置き換えて無効化した後に取得失敗 | 新しい本文を取得するまで現在の編集欄を保持 |
| 原稿取得待ちに追加入力・別の移動 | 遅い取得結果で現在の本文を置き換えられた | 取得の順序、編集対象、作品、クラウド、本文の変化を確認して古い結果を破棄 |
| 未編集の原稿への外部反映 | 外部確認後にopenFileでもう一度本文を取得 | 取得済み本文をそのまま反映して二度読みをなくす |
| 保存中に本文を元へ戻してタブを閉じる | dirtyがfalseだと警告しなかった | 保存中もbeforeunloadの警告対象とする |

接続解除・ログアウトで破棄を承認した場合は、予約済みの自動保存を取り消す。保存中の追加入力は引き続き保持する。競合を無視する上書きや自動リトライは追加していない。

## 検証

`test/web-manuscript-save.test.mjs` に17件を追加した。app.mjsの実際の関数・イベントハンドラをVMで実行し、通信を模擬して完了順を制御する。文字列の存在確認だけではなく、本文・版情報・未保存状態・副作用を検証する。

- 保存中の追加入力、通信失敗、競合、保存中の移動抑止。
- metadata・本文取得中の保存完了、外部取得中の追加入力、クラウド切替、改行だけの外部更新。
- 読み込み失敗、遅い応答、二重読み込み、取得済み本文の再利用。
- 接続・解除・ログアウトのキャンセル、保存中のタブ終了警告。

第0段階で保存した修正前のapp.mjsでも同じ検証を実行し、修正対象の失敗を再現した。再現用ファイルとログは `.review-baseline/stage1-original-tests.mjs` と `stage1-original-results.log` に保存。

修正後は全体**378件すべて成功**。サンドボックスの一時フォルダは前回同様にワークスペース内を指定した。ログは `.review-baseline/stage1-tests.log`。app.mjsとsw.jsの構文確認も成功。

既存のHOME画面テストは、本文取得に必要な模擬providerと編集欄を追加した。HTMLの参照を `app.mjs?v=1.0.158`、Service Workerを `mojigoto-shell-v200` にそろえた。本番へのアップロードは実施していない。

## 確認の限界と次の作業単位

実クラウド・ブラウザ・スマートフォンでは未確認。タブ終了警告はブラウザの制約を受けるため、入力内容の永続的な復旧を保証する機能ではない。

次は各クラウドの保存処理と同時更新を点検する。特にGoogle Driveの実装は、版の事前比較後にPATCHを送っており、比較から書き込みまでの間に別端末が更新した場合の保護を今回のVMテストでは確認していない。APIの条件付き更新の可否を調べ、実アカウントでの確認範囲も決める。

VS Code側では原稿保存をエディタに委ね、保存イベントから執筆記録・バックアップの処理を呼ぶ入口を確認した。付随データの失敗時処理、ノート・構想メモ、バックアップ復元、改名・並び替えの途中失敗は未点検。原稿のクラウド保存確認後に、それぞれ別の作業単位で扱う。

ローカルソースだけを更新し、利用者の作品データ・環境設定・本番は変更していない。
