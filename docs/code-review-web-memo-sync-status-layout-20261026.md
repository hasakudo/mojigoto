# メモの保存・反映中表示とスタイルの修正（2026-10-26）

## 報告

利用者より全体設定の機能確認後、次の指摘を受領した。環境指定はなく、本番・テスト両方で確認済みとは広げない。

- 初回に同期競合ありとなり、項目メモからの手動反映自体は成功しても競合バッヂが残る。
- 項目メモの保存後、移動しようとするまで保存済みに見え、反映中への切替が遅い。
- 構想メモ側にも反映中バッヂが必要。
- 歯車メニューの横スクロール、項目メモの個別設定セレクトのスタイル不足。

## 原因と修正

ノート・構想メモの保存本体は、書込成功直後に保存済みと表示し、その後のバックアップ等をawaitしていた。そのため、実際には保存処理の途中で移動を止められるのに表示は完了して見えていた。保存後の付随処理も保存中のまま保持し、そのまま反映へ進む場合は反映中へ切り替える。保存済みを途中で先に表示しない。

項目メモからの手動反映は、反映先が同内容なら早期returnしていた。その場合も成功時も、最後に残る競合を確認してステータスを更新する。差分なしであっても古い競合バッヂを解除する。ただし別項目に未解決の競合があれば同期競合ありを維持する。両側変更や初回同期の方向不明を自動上書きする変更は行わない。

手動反映にも専用の処理中状態を持たせ、読込開始から終了まで反映中と表示する。内部のノート保存や追加入力がステータスを更新しても、反映中を保つ。失敗した場合は失敗／未保存を表示し、成功と誤認させない。

構想メモ側は、従来は反映方向を決めた後にのみ同期中フラグを設定していた。出典ノートの探索・読込前から同期中と反映中を保持するよう変更し、既存の画面移動ガードとページ離脱の警告条件を全区間へ適用した。保存中は保存中、反映先の読込から二つ目の保存の終了までは項目メモへ反映中、完了後に保存済みへ戻す。エラーや未解決競合を成功表示で消さない。

構想メモの出典読込中に追加入力があった場合は、従来の文書照合で古い反映を止め、未保存を維持して次の自動保存を予約する。反映処理内の同期情報保存では、バッヂと保存ボタンを途中で完了状態へ戻さない。

スタイルは次を修正した。

- 歯車パネルのグリッド列・子要素を縮められるようにし、長い全体設定名を折り返す。チェックボックスの幅を保ち、内容を隠して横スクロールを消す方法は使わない。
- 項目メモの個別設定セレクトと構想メモのSOURCE欄セレクトへ、既存のテーマ変数による色・枠・角丸・余白・タップ高さを適用する。

## 検証

追加8件を含む全体npm testは1,480件成功、失敗0・スキップ0。構文チェックも成功。反映失敗と追加入力が重なったときに失敗表示を未保存だけの表示で消さないことも確認した。

- ノートと構想メモの本体保存後、バックアップ待ちの途中で保存済みを表示しない。
- 手動反映が差分なしでも古い競合バッヂを解除し、別項目に競合があれば維持する。
- 構想メモの出典読込待ちから反映中を表示し、画面移動を止める。
- 出典読込中の追加入力を上書きせず、未保存と次の保存予約を保持する。
- 内部保存や入力更新によって反映中表示が途中で保存済みへ戻らず、エラー表示は維持する。

実際のapp.mjs・保存／同期モジュール・画面イベントを、メモリー上の検証用ノートと構想メモで確認した。

- 375px幅・緑テーマで、歯車メニューの長いラベルが折り返し、横スクロールが出ないことと、セレクトの色・枠・余白を画像で確認した。
- 両側変更を再現し、項目メモ保存後の同期競合ありを確認。その後、項目側から手動反映して両側の本文が一致し、バッヂが保存済みに戻った。差分なしの再反映でも競合バッヂが残らなかった。
- 項目メモ側の自動反映は、移動操作を行う前から反映中バッヂを表示した。
- 構想メモ側も、保存中表示から出典の遅延読込中に項目メモへ反映中へ切り替わった。12秒の読込待ちで、移動操作より先のバッヂ表示と移動時の反映中通知を確認した。
- 単独ページのログと最終反映結果はbrowser-results.jsonへ保存。375px埋込ホストで起動時に記録されるMutationObserverの対象エラーは過去の検証ホストでも記録したものと同形で、console-host.jsonへ残した。単独ページとは分け、ブラウザ全体がエラー0とは扱わない。

実設定やAPIデータを検証サーバーから配信していない。証跡は.review-baseline/web-memo-sync-status-layout-20261026/に保存。

反映後は、何も移動操作をしなくても両画面で保存中→反映中→完了の表示となること、手動反映後に解消した競合表示が残らないこと、歯車メニューと個別設定セレクトの表示を確認する。初回に真の両側変更がある場合の競合停止自体は維持している。実作品で意図的な競合や失敗を作る必要はない。
