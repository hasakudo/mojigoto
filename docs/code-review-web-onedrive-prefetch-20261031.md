# OneDriveのタグなし環境で子・管理一覧を先行一括取得（2026-10-31）

## 実機計測による切り分け

利用者が初回表示と変更なし2回の再読み込みを報告。初回はカタログなしで基本情報13,547ms。再読み込みでは先行表示8ms／4ms、最新取得8,457ms／11,965ms。両方ともtagCacheEnabled=true、cachedFolders=10、matchingDrives=10、snapshotIssues=noneだが、子・管理ともcurrentTags=0、cachedTags=0だった。

この接続の通常一覧で判定に使うフォルダcTagが得られず、既存キャッシュと親・driveの照合が正常でもcTag再利用は適用できないことが分かった。provider機能の無効化やカタログ欠損を原因とする仮説は再読み込み結果から除外できる。生のクラウド応答や契約種別を調べたものではないため、Business等のアカウント種別までは断定しない。前回の条件を緩めず、タグを必要としない通信順の改善へ進めた。

## 変更

前回カタログがあるタグなしのMulti作品について、前回の.mojigotoのIDを「新しい取得を早めに始めるため」だけに使い、現在の作品直下の子一覧と管理一覧を同じbatchへ入れる。10作品ならGET20件を1回のPOSTへまとめる。前回の子一覧や設定本文を無条件に最新情報として採用する処理ではない。

1. 最新のルート一覧で、現在存在する作品だけを対象にする。
2. 前回の作品とID・driveが一致し、前回.mojigotoの名前・親・driveが妥当な場合だけ、子一覧と前回管理IDへの一覧GETを先行する。タグが得られる作品には従来のタグ検証・再利用を維持する。
3. 新しく取得した子一覧から現在の.mojigotoを特定する。先行先のID・親・driveと一致し、返った各子の親も一致する場合だけ採用する。
4. .mojigotoが作り直された／別の場所にある、先行の返答が失敗・不正、前回情報が不十分なら、現在確認した管理先を従来どおり取得する。空になった管理一覧も新しい空一覧として扱い、前の設定を残さない。
5. 追加作品は探索し、ルートから消えた作品の前回管理先を要求しない。設定・共有集計の本文は新しく取得したファイルの版で確認する。

OneDriveProviderにlistChildrenBatchSettledを追加。一括応答の項目ごとの失敗をErrorとして分離し、古い先行先の404が現在の作品一覧を巻き込まないようにした。現在の子フォルダの失敗は通常の上限付き一括取得へ戻し、実際に取得できなければ全体成功にしない。batch全体の失敗も通常取得へ戻す。429は即座の再送・個別連打をしない。従来のlistChildrenBatchは既存の呼出元向けのエラーとフォールバックを維持し、ページ続きの取得も共用する。

要求は作品と管理先を交互に並べ、[Graph JSON batchingの20件上限](https://learn.microsoft.com/en-us/graph/json-batching)を守る。Dropbox／Google Driveや参照専用探索にはこの先行処理を適用しない。既存の書込、条件付き保存、関連設定の最新確認は変更しない。

## 計測の見方

子フォルダ一覧にprefetchedFolders（先行要求した管理フォルダ数）、管理一覧にprefetchedFolders（照合後に採用した数）を追加した。管理一覧のfoldersは後段で改めて取得した数。例えばタグなし10作品で管理一覧がfolders=0／prefetchedFolders=10なら、管理情報を子一覧と同時に新規取得できたことを示す。reusedFoldersは0のままで正常。

管理フォルダの通信時間が子フォルダの区間へ移るため、子と管理の合計、作品一覧・基本情報完了で比較する。個別の子区間だけで遅くなったと判断しない。前回カタログがない初回は管理先をまだ特定できないため、従来の2段階取得を維持する。
