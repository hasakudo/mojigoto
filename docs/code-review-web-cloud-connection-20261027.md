# 接続・履歴の整理2-B1：自動接続と起動時の接続処理（2026-10-27）

## 承認と前段の確認

利用者から作品設定の編集・自動／手動保存・表示・反映を確認し問題なしとの報告と、次へ進む承認を受領。2-A5は利用者確認済みとして扱う。報告内で確認環境が個別に明示されたわけではないため、端末・クラウド・環境の網羅確認とは扱わない。

予定どおり接続・履歴復元の整理へ進む。最初の単位として、自動接続設定の保持と、起動時の認証応答・作品ルート選択・保留中履歴復元の順序を分離する。

## 変更

web/lib/cloud-connection.mjsを追加。createAutoConnectionControllerが以下の5関数を返す。

- autoConnectStorageKey
- readAutoConnectPreference
- saveAutoConnectPreference
- rememberConnectedCloud
- reconnectPreviousCloud

createConnectionInitializerはinitializeConnectionを返す。認証provider・設定読込・利用者認証・クラウド選択・作品一覧・履歴復元・DOM表示を注入し、接続先と利用者を確認しながら各段階を進める既存の順序を保つ。2つのコントローラに分け、自動接続設定と起動処理の依存を区別した。

6関数の処理本体は移動前と一致することを確認。自動接続設定の利用者別保存、認証失敗／取消後10分の再試行抑止、Googleの認証指定、既に有効な接続の再利用、クラウド別の認証応答、保留中履歴の利用者確認を維持する。

接続・認証ボタンのイベント、各クラウドのauth実装、既存セッションの認証情報、接続先を有効化するactivateCloud、作品一覧取得、履歴保存・表示と具体的な画面復元、ブラウザ戻る／進む、スクロール位置復元、未保存の破棄判断はapp側と既存モジュールに残す。新しいログインフロー、権限、トークン形式、履歴形式は導入しない。

既存のソース抜き出しによる自動接続テストと起動接続テストは、新モジュールを実際に呼ぶよう更新。実行中に接続先・利用者・復元処理が切り替わるテストの依存も維持し、検証を削除しない。

## 検証

全1,559件成功、失敗0。追加5件で自動接続設定の保存領域が使えない場合、再試行抑止期間経過後の認証、利用者認証未完了時の停止、トークン取得待ち中の利用者変更、未接続Googleから別クラウドへ勝手に切り替えないことを確認した。

既存テストでも3クラウドの接続分岐、保存済み作品ルートへ直接戻る動作、別クラウドのトークンを使わないこと、接続切替後の古い結果抑止、認証キャンセル、保留中履歴の復元と復元先切替後の失敗案内、未保存時の復元停止を確認。6関数の一致はfunction-comparison.json、全体テストはfull-tests.logへ保存。変更JavaScriptの構文確認も実施した。

今回の検証は模擬auth・providerを使った自動テストであり、実際のOAuth認証・再同意・実クラウド上の履歴復元を実行したものではない。
