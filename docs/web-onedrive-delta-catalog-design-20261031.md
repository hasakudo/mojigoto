## 次の候補：差分APIで変更なしを確認する

[Microsoft Graph driveItem: delta](https://learn.microsoft.com/en-us/graph/api/driveitem-delta?view=graph-rest-1.0)は、初回に状態を取得して以後の差分をdeltaLinkで追跡するAPI。token=latestによる最新チェックポイント、ページ継続、削除、期限切れ410の再同期が定義されている。本文を取得するAPIではなく、メタデータの変更追跡として検討する。

最初の機能範囲は「正しく対応付けた一覧があり、差分がないことを確認できた場合に一覧探索を省く」に限定する。差分があった場合の増分マージ、全作品の更新処理、ノート保存・同期の変更は初期実装に含めない。変更あり・判定不能・API非対応・期限切れでは通常の最新取得へ戻す。

## 最初の作業単位と条件

1. **選択した作品ルートで対応可否を確認する読取処理。** 公式ページにはdrive rootのHTTP例とitem IDによるSDK例があるが、今回の接続先の任意フォルダで利用できることは未確認。選択フォルダを対象に確認し、非対応だからといって無断でDrive全体の列挙へ広げない。取得件数・ページ数・時間・結果種別だけを計測する。
2. **初期状態とトークンの対応を設計・検証する。** 既存キャッシュへ後からtoken=latestを付けただけで変更なしと扱う実装は不可。初回delta列挙から作る基準か、開始チェックポイント→通常の完全取得→差分再確認で変化なしを確認する基準を選ぶ。取得が不完全な一覧、設定本文を読めず仮のタイトルになった一覧、途中失敗にトークンを対応付けない。
3. **キャッシュとトークンを一緒に確定する。** 利用者・クラウド・drive・作品ルート・取得世代を照合し、同じ取得結果へ対応付けたものだけを保存する。古い集計処理や別タブが新しいトークンを古い一覧へ付けないよう、呼出元ごとの結果に束縛する。切断・ログアウト・保存先変更・キャッシュ破棄で整合性を失った追跡情報も失効させる。
4. **変更なしの場合だけ高速化する。** 全必要ページを確認し、変更なしを判断できない応答を成功扱いにしない。変更ありの場合は従来の探索へ戻す。原稿・ノート・設定の更新、改名・移動・追加・削除を取りこぼさない。初回や更新直後に追跡を確立するコストは別計測する。
5. **失敗時は既存の操作を保持する。** 期限切れ410、400／403／404、通信失敗、ページ上限超過、循環リンク、不正応答では通常取得を使う。何度も失敗する追跡確認を毎回追加して遅くしない設計が必要。

リンクは同じGraphの許可済みエンドポイントと範囲を検証する。差分トークン／URLはOAuthトークンとは別だが、不透明な追跡情報として扱い、速度計測や共有ログに出さない。未保存の編集内容や現在の画面には触れず、既存の先行表示を維持する。

初期候補は上記の対応確認とキャッシュ整合性設計まで。初回delta全列挙と、通常取得の前後にチェックポイントを置く方式のどちらを採るかは、対応範囲・ページ量・実機負荷を確認して決める。小さい画面でのメタデータ保持量、ページ／時間の上限も決めてから、通常一覧へ接続する。実機での対応・速度はまだ未確認であり、「1回で必ず速くなる」とは扱わない。
